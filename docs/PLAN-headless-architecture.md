# Headless architecture — managing Fieldhouse without a CMS backend

## Context

The POC is a static reference site: 2,231 pages generated by `site/build.py` from one
parsed specimen, deployed as files. The owner's question: a real version needs to be
*managed* — new results arriving weekly, corrections, rosters — without acquiring a
server-backed CMS. How should that be architected headless?

The system already has the right separation and the answer falls out of it:

```
records  ──▶  registry  ──▶  renderer  ──▶  static tree
(source of      (site/build.py today)         (Vercel)
 truth)
```

What's missing is not a CMS — it's that **records don't exist as a managed layer yet**.
Today the build parses the PDF specimen directly, so the "database" is a binary file
and the parser. Everything below follows from fixing that one thing.

The bet: **git is the headless backend.** Results are append-mostly, low-volume (a few
hundred writes a week per state at peak), need review, benefit from history, and cost
nothing to store. A PR is a moderation queue; a merge is a publish; a revert is a
correction; `git log` is the audit trail the extraction-only policy already demands.
And structurally, "a repo of records per school" is the same mental model as an
AT Protocol repo per school — so the git phase is not a detour from protocol-native,
it is the same architecture on a swappable substrate.

On why the substrate matters at all (owner's framing, adopted): this is public data,
so "data ownership" is not the point — **portability is**. Records in an open schema
on a swappable store mean nothing is vendor-locked, including to this tool itself: the
whole thing can be rebuilt elsewhere without losing the data layer.

## The three planes

**Records plane** — canonical JSON, one file per contest, plus org files (schools,
conferences). The JSON shapes are the dataclasses in `app/shapes.py` serialized, and
they double as the draft `org.prepnet.*` lexicons — writing them to disk IS the schema
work Phase B needs.

**Management plane** — how records get created and changed. The key correction from
the owner: **most sports have no Hy-Tek equivalent.** Tennis has nothing; golf has
iWanamaker; several sports have no tool at all — which is exactly why the third-party
management tools exist, and absorbing that role is part of what this solves. So manual
entry is not a fallback behind upload; the two are co-equal writers, and entry is the
unsolved one. Three writers, all converging on the same records directory via the
GitHub API; none needs a server the owner operates:

1. **Shape-native entry forms** — the anti-third-party-tool surface. One static form
   per contest shape, not a generic JSON editor: the DUAL form knows about ordered
   lines and set scores (cheesybook's report-a-dual is the proven prototype,
   generalized), the GAME form knows about periods, the small-MEET form handles a
   tri-meet's marks. Submission goes through one serverless function that validates
   against the shapes and opens a records PR — or commits directly for a trusted
   scorekeeper role. This is the surface that replaces "there's just not anything" for
   tennis, golf, and the rest of the untooled calendar.
2. **Upload → parsed PR** — for the sports that DO have tools. A drop-a-file page
   backed by one serverless function (the repo already deploys to Vercel; functions
   live beside the static tree). It runs the matching adapter
   (`ingest/adapters/hytek_pdf.py` today, iWanamaker/CSV/HTML adapters as they're
   captured), writes canonical records with provenance + confidence, and opens a PR.
   Review-then-merge is the review queue the extraction-only policy requires.
3. **Org-data editing + god mode** — rosters, school info, conference membership via
   Sveltia CMS (static `admin/` + GitHub OAuth, no server) or direct commit.

**Render plane** — unchanged. A GitHub Action (the `build-letterboxd.mjs` pattern the
owner already runs) rebuilds on any push touching `records/**` and commits the
generated tree; Vercel redeploys. Publish latency is one Action run (~1–2 min), which
is fine for results. If a live game-night scoreboard ever matters, that is one small
JSON endpoint the front page polls — additive, later, and it does not change this
architecture.

## Phase B — the protocol substrate (deferred, not dropped)

When the lexicons have been shaped by real Phase-A use: school identity becomes a DID,
records move from repo files to `org.prepnet.*` records in per-school PDS repos, and
the builder consumes one Jetstream subscription filtered on the prefix instead of
reading `records/`. **Only the loader changes** — registry, renderer, page types, and
the writers' UX survive intact. Sveltia is replaced by an OAuth writer app against the
school's own repo. This is why Phase A serializes records in lexicon-shaped JSON now.

## Phase A changes (concrete)

| File | Change |
| --- | --- |
| `app/records_io.py` (new) | serialize/deserialize `app/shapes.py` dataclasses ↔ JSON; shapes stay the single model |
| `records/` (new) | `contests/<season>/<slug>.json` · `orgs/schools.json` · `orgs/conferences.json` |
| `ingest/run.py` (new) | CLI: source file → records + provenance report; the specimen parse becomes a one-time ingest that populates `records/` |
| `site/build.py` | load from `records/` instead of calling `hytek_pdf.parse` at build time; registry/renderers untouched |
| `.github/workflows/build.yml` (new) | on push to `records/**`: run build, commit generated tree |
| `report/` (new) | shape-native entry forms: dual first (cheesybook pattern), then game, then small-meet |
| `api/submit.py` (new) | Vercel function: form payload → validate against shapes → records PR (or direct commit for trusted role) |
| `api/parse-upload.py` (new) | Vercel function: file in → adapter → PR with records |
| `admin/` (new, later) | Sveltia `index.html` + `config.yml` for org data (schools, conferences, rosters) |
| `docs/AAR-…` | append the headless architecture decision to the record |

Order within Phase A: records extraction + build-from-records first (the load-bearing
refactor — everything else bolts onto it), then the Action, then the **dual entry
form** (the untooled-sport solve, and cheesybook proves the interaction), then
upload-PR, then the org-data admin.

## Decision points held open

- **When Phase B starts** — recommendation: after one real season's worth of Phase-A
  use has stabilized the record shapes, not before.
- **Trusted-scorekeeper direct commit vs everything-through-PR** — start with
  everything-through-PR; loosen per role once volume justifies it.
